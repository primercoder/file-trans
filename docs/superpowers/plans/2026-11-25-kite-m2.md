# Kite M2 实施计划：密文文件传输、断点续传、存储配额与身份导出

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:execating-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 交付 E2EE 文件传输：客户端信封加密分块上传/下载（可断点续传），服务端密文文件仓库 + 存储配额淘汰（含"已被清理"提示），身份导出/导入（换机迁移），storage_used 实装。Linux 全流程测试通过后，代码部署到 Windows 虚拟机（桌面）完成 Windows 侧编译与测试。

**Architecture:** 在 M1 的 workspace 上增量：`kite-core` 增加文件加密模块（FK + 分块 AES-256-GCM）与 Engine 文件收发/续传/身份导出导入；`kite-server` 增加 filestore（密文分块落盘 + SQLite 元数据 + 配额淘汰）。文件消息沿用 M1 加密信封通道（type=file），服务端只接触密文块。

**Tech Stack:** 沿用 M1（Rust 1.99, axum 0.8, tokio, rusqlite, chacha20poly1305, hkdf, sha2, reqwest）；新增 argon2 已在 M1 引入。

**Spec:** `reference/tech-design.md`（§4 数据模型 file_refs/files、§5 存储配额与淘汰、§6 传输协议要点、§9 导出身份列入 M2）

## Global Constraints
- 服务器只见密文：文件块、文件名、FK、元数据全部密文；服务端不得有明文回退路径
- 文件密钥 FK 随机生成；文件用 FK 做 AES-256-GCM 分块流式加密；FK 用收发双方会话密钥加密后随文件消息信封发送（信封加密）
- 未 ACK 的**消息**不占配额（M1 已实现）；**文件**均占配额，淘汰顺序见 Task 4 裁定
- 密码学不自造：分块加密基于 chacha20poly1305 + HKDF 派生每块 nonce；分块加密必须有 KAT
- 所有新端点走 TLS 1.3 + Bearer 鉴权；错误处理遵循 M1 的 ApiError 模式；无生产 unwrap
- 每个任务完成即 commit；测试全部通过才能 commit；clippy -D warnings 干净
- 测试约定沿用 M1：跨包 server 二进制经 `CARGO_BIN_EXE_kite-server` 显式传递；测试进程各自绑定临时端口（含 KITE_HEALTH_BIND）

## Review Focus
- 服务端不得依据明文做任何决策（淘汰按元数据 created_at/downloaded_at，不碰内容）
- 续传语义：客户端中断后重续不得产生重复块或缺口；上传完成前文件不可被下载/计入投递
- 淘汰边界：淘汰"未接收"文件必须先投递占位提示且不丢消息通道语义；配额计算与实际落盘字节一致
- FK 安全：FK 只出现在加密信封内；导出档案必须经口令加密（Argon2id + AEAD）

### Task 2: 客户端文件加密——FK、分块流式 AEAD 与 KAT
**Files:**
- Create: `crates/kite-core/src/file_crypto.rs`
- Test: `crates/kite-core/tests/file_kat.rs`

**Interfaces:**
- Produces:
  - `FileKey::generate()`（32 字节随机 FK）
  - `encrypt_file(fk, reader, chunk_size=256KiB) -> (FileHeader, Vec<EncryptedChunk>)`；`FileHeader { fk_nonce 绑定域, total_chunks, chunk_size, content_hash: SHA-256(密文全量) }`（header 本身含元数据但不含文件名；文件名放消息信封层）
  - `decrypt_file(fk, header, chunks) -> Vec<u8>`（流式 API：`ChunkCipher::new(fk, header)` + `push_chunk`，支持乱序到达后按序输出）
  - 每块 nonce = HKDF(fk, "kite-file-v1" || chunk_index) 派生；AAD = header 的域分隔 || chunk_index || total_chunks（防块重排/跨文件移植）
  - KAT：固定 FK/明文块 → 钉住首块密文 hex 与 content_hash（预期输出断言，非自洽）
- 错误处理：块 MAC 失败/索引越界/块数不符 → 结构化错误，不 panic

### Task 4: 存储配额与淘汰——eviction 顺序、占位提示、stats 实装
**Files:**
- Modify: `crates/kite-server/src/filestore.rs`、`crates/kite-server/src/api/files.rs`、`crates/kite-server/src/api/stats.rs`、`crates/kite-server/src/config.rs`
- Test: `crates/kite-server/tests/quota_eviction.rs`

**Interfaces:**
- Produces:
  - init 时配额检查：`可用 = KITE_MAX_STORAGE_BYTES - Σ已存文件字节`；不够 → 按 created_at 从最早开始删**已接收**(downloaded_at 非空)文件 → 仍不够 → 从最早删**未接收**文件并投递 `type=file_evicted` 信箱条目（body: {file_id}）→ 循环；文件本身 > 配额上限 → 413 拒收
  - **裁定（eviction 顺序权威口径）**：已占 = 所有已存文件字节（含未接收）；未接收文件仅在已接收文件删尽后才可被淘汰，淘汰时必须先投递 file_evicted 提示再删块（占位提示不可丢）
  - `GET /stats` 的 `storage_used` 实装为 filestore 实际字节（替换 M1 硬编码 0）
- 淘汰为同步路径的一部分（init 内联执行），M2 不做后台任务
