# 加密模型（对称主体 / 非对称握手）

## 结论

**只有握手与身份证明使用非对称密码；消息、文件、群消息的"主体"全部是对称 AEAD。**

| 数据 | 算法 | 密钥来源 |
|---|---|---|
| 注册/登录签名 | Ed25519（非对称） | 设备长期身份密钥 |
| 配对握手 | X3DH：X25519 + Ed25519 验签（非对称） | 每次配对一次，可异步离线 |
| 消息正文 | ChaCha20-Poly1305（对称 AEAD） | 双棘轮每消息派生密钥 |
| 文件块 | ChaCha20-Poly1305（对称 AEAD） | 每文件随机 32 字节 FK |
| 文件密钥分发 | 消息正文内（对称 AEAD） | 双棘轮会话密钥；不使用非对称加密文件本身 |
| 群组消息 | ChaCha20-Poly1305（对称 AEAD） | 群组 Sender Key（32 字节随机） |
| 群密钥分发 | 消息正文内（对称 AEAD） | 各成员的配对会话密钥 |
| 身份备份 | ChaCha20-Poly1305 + Argon2id（对称+口令 KDF） | 用户口令 |

## 密钥层级

1. **长期身份**：Ed25519 密钥对，`device_id = SHA-256(公钥)`。
2. **配对握手**：X3DH（IK/SPK/OPK/EK）派生共享根密钥 `SK`；这是唯一按会话执行的非对称步骤。
3. **双棘轮（Double Ratchet）**：
   - 对称链：每条消息由链密钥经 HKDF 派生新消息密钥，ChaCha20-Poly1305 加密正文；
   - DH 棘轮：仅在发送方向切换时引入新的 X25519 公钥（消息头携带），用于前向保密与妥协后自愈。**正文仍是对称加密**，DH 只是链密钥轮换的输入。
4. **文件**：发送端为每个文件生成独立随机 FK（32 字节），文件块用 FK 做 ChaCha20-Poly1305 分块加密（256 KiB 明文块）；FK、文件名、头信息放进一条普通消息正文，经配对会话对称加密后发送。因此文件路径上没有逐文件非对称开销，也不暴露明文。
5. **群组**：创建者生成 32 字节群密钥，作为 `group_key` 消息正文经每个成员的配对会话（对称）分发；群消息用群密钥 ChaCha20-Poly1305 加密，服务器按成员表扇出。

## Nonce / AAD 设计

- 消息：双棘轮消息密钥只使用一次，ChaCha20-Poly1305 nonce 由会话状态派生，天然唯一。
- 文件块：`nonce = HKDF-SHA256(FK, "kite-file-v1" || chunk_index_be_u32)`；FK 每文件随机，因此确定性 nonce 不会跨文件复用；AAD 绑定版本域、块索引、总块数、块大小，防重排/跨文件移植。
- 群消息：每条消息随机 96-bit nonce；AAD 绑定 `kite-group-v1|group_id|sender|seq`，配合接收端每发送者单调序号高水位抑制重放。
- 信封时间戳 ±120 秒窗口；文件 `size` 与实际密文字节严格相等校验。

## 内存与性能

- 发送文件使用 `encrypt_bytes`：按切片直接加密，不再保留明文副本，峰值内存约为「密文 + 调用方已持有的文件字节」。
- 密文块按 256 KiB 上传，支持断点续传；相同 FK + 相同参数可确定性重放，重试不会产生不一致块。
- 群消息只需一次 AEAD 加密，服务器扇出 N 份密文。

## 已知边界

- 密钥 zeroization 尚未实现（规划中）。
- 平台安全存储（keyring/DPAPI/Keystore）待接入，当前仅依赖文件权限。
- 群组文件传输未实现（M5 仅文本）；群密钥轮换目前由创建者单密钥分发，成员变更需重新分发。

## 威胁模型：服务器被入侵

设计目标是让服务器只承担**中继与临时密文存储**：消息、文件、群消息在离开客户端前完成加密，服务端只保存密文和投递所需的最小路由信息。

| 攻击者能力 | 能读到明文吗 | 说明 |
|---|---|---|
| 拖库 / 磁盘或备份泄露（被动） | 否 | 服务端只有身份公钥、签名预密钥、一次性预密钥公钥、密文书信、文件密文块；签名私钥、棘轮状态、文件密钥都在客户端 |
| 在线被动（TLS 终结、抓包） | 否 | 仅 TLS 1.3；默认校验 WebPKI 根证书，自签名部署可改用证书指纹固定；正文另有端到端加密 |
| 主动篡改响应 / 改数据库 | 已配对会话：否 | 消息需通过双棘轮 AEAD；预密钥包与设备 ID 绑定校验阻止替换对端；群消息有发送者签名 |
| 主动攻击**首次配对** | 见下 | 目录内容（设备名 → 设备 ID）由服务器提供，需用安全码或线下交换设备 ID 来消除信任 |
| 长期主动 + 拿到客户端设备 | 是 | 本地 SQLite 尚未接入 keyring/DPAPI/Keystore，属于已知边界 |

具体机制：

- **配对绑定**：`device_id = SHA-256(IK_pub)` 前 16 字节；发起方在取回预密钥包后本地重算并比对设备 ID，服务端无法用自己生成的密钥回答别人的设备 ID。响应方同样校验请求信封里的 `ik_pub` 与发送者设备 ID 一致。
- **带外核验**：双方可从各自会话（其关联数据已被每条消息认证）派生同一个 60 位安全码，用于当面/其他渠道核对；也可直接粘贴 32 位设备 ID 配对，完全绕开服务器目录。
- **群组发言**：群密钥经成员各自的配对会话分发，信封中附带成员身份表（`device_id → IK`，逐项校验哈希一致）；每条群消息由发送者 Ed25519 签名，接收方按名单验签后再解密。恶意成员（或与服务器合谋者）无法把消息冒名为其他成员。
- **重放与错投**：棘轮消息密钥一次性使用；群消息带每发送者单调序号高水位；文件块 AAD 绑定块索引/总数/块大小并有整段密文哈希。

账户与联系人的生命周期同样是端到端处理的：删除联系人会发出一条经棘轮加密的 `unpair` 通知，对端收到后删除会话但保留本地历史，并把联系人标记为「对方已移除」；注销账户时服务端删除该设备的信箱、文件、群组与预密钥，并向所有设备投递 `device_deleted` 通知，对端把联系人标记为「对方已注销」，历史仍可只读查看。只有用户自己手动删除联系人才会清除本地会话与历史。服务器只保留路由与发现所需的设备注册表，不保存联系人列表。

服务端仍然可见的元数据：谁在何时给谁发了多少字节、`kind` 字段、设备名、群名、设备在线状态与最后活跃时间、文件大小与块数。服务器还可以拒绝服务：丢弃、延迟、冻结消息，或诱导客户端重新配对（客户端会重新校验设备 ID，但用户仍应核对安全码）。

不在当前范围内：密钥透明度日志（key transparency）、消息长度填充、客户端本地存储加密、群成员变更时的密钥轮换。
